## Why（为什么做）

用户 2026-09-21 提出隐私关切。复核发现（实测，非推测）：

1. **本机绝对路径**：`git grep -lE '/home/[a-zA-Z0-9_.-]+'` 命中 **49 个已跟踪文件 / 100 行**，其中 `~` 占 **91 处**——暴露本机用户名、项目绝对路径与本地 profile 布局。其中一份**早先的 `security-privacy-audit` 归档自己就记录了这个问题但没有清理**。
2. **不该入库的文件**：**6 个 `.pyc`**（Python 字节码内嵌绝对源码路径）+ **1 个 `.bak`** 被跟踪，而 `.gitignore` 已有 `*.pyc` / `__pycache__/`（先入库、后加规则）。
3. **未推送窗口**：`develop` 领先 `origin/develop` **37 个提交**，远端停在 `19b3463`（2026-09-11）——**历史仍可重写**。
4. 已核对**不是**问题：无真实凭证入库（历史扫描 0）；`/home/...`、`/home/user`、`/home/ubuntu` 是通用占位符；`hyhmrright@gmail.com` 是 brooks-lint 上游作者在 vendor 元数据中的公开邮箱（上一轮审计已判 FALSE_POSITIVE）；无私网 IP、无本机 hostname、无用户私人邮箱。

## What（做什么）

1. **前向脱敏**：把 49 个已跟踪文本文件中的 `~` 归一为 `~`（代码类文件按语义改写为可运行形式）。
2. **停止跟踪**不该入库的 6 个 `.pyc` + 1 个 `.bak`（`git rm --cached`），并补 `.gitignore` 规则（`*.bak`；`*.pyc`/`__pycache__/` 已存在）。
3. **历史清理**（用户选定）：用内建 `git filter-branch` 对**未推送的 37 个提交**做同样替换 + 移除这些路径，使 `~` 不再存在于任何可达提交中。
4. **可追溯性**：记录 **old→new 提交哈希映射**，并登记「哪些文档引用了被重写的哈希」（这些引用会失效）。

## 验收线（粗粒度）

1. `git grep -lE '~'` 在**工作区**与**全历史可达提交**中均为 **0 命中**。

3. 仓库既有门禁不退化：`make check` 六门全绿。

## 风险与未知

- **历史重写**：37 个提交哈希全变；文档中引用这些哈希的位置会失效（需登记）。已用 `git bundle` + tag `pre-scrub-backup` 做安全网。
- **`sed` 误伤**：替换范围限定为字面量 `~`，且逐文件 diff 复核。
- **本地对象残留**：重写后必须清 `refs/original` + reflog + `gc --prune=now`，否则旧对象仍可恢复（对「隐私」而言等于没清）。
