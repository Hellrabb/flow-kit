- **创建日期**: 2026-07-07

## Why（为什么做）

在 5/6/7 阶段，L2/L3 独立审查发现代码问题后，agent 存在三种"浮于表面"的行为模式：

1. **文档标记式逃避**：在 INDEPENDENT-REVIEW-<N>.md 里写「⚠️ 未覆盖 / 暂不处理」就结束，代码一行不改
2. **长篇分析零行动**：详细分析问题根因和影响，但最终不产生任何代码变更
3. **记一笔了事**：把问题写入 LESSONS.md 作为"技术债"登记，源码问题原封不动

根因：当前 prompt 指令的"修复代码优先"约束不够硬；gate 层的 `.done` 校验只查存在性和真实性，不查实效性——agent 可以通过写文档（低成本路径）绕过去，而不修代码（高成本路径）。

**影响**：L2/L3 独立审查花了 token 和外部模型调用成本，但实际代码质量没提升——审查产出被"文档化"消解掉了。

## What（做什么）

在 prompt 层和 hook 层同时加固，确保 L2/L3 审查发现的问题**必须落到代码变更上**，不能只存在于文档里：

- **Prompt 层**：5-test / 6-review / 7-integration + L2-blind-review.md 增加「修代码优先」强制协议，每个发现必须对应代码修复或显式技术债登记
- **Hook 层**：gate hook 增强实效性校验——检测"纯文档响应"（发现 >0 但 diff 只含 .md）、校验"已修复"声明对应的源文件确实被修改

## 范围排除（这次不做）

- 不改动 L2/L3 审查内容生成逻辑（审查发现的质量本身不在本次范围）
- 不新增独立 hook 模块（复用现有 gate-integrity + independent-review-gate 框架）
- 不改变 gate_config 预设体系
- 不做"自动修复"——agent 仍需人工执行修复，本次只加固"必须修"的约束

## 验收线（粗粒度，不是 AC）

1. 在 5/6/7 任一阶段，L2/L3 发现代码问题后，agent 不能仅通过写文档通过 gate——必须产生源码变更或显式技术债登记（含理由）
2. Hook 层能检测并阻断"纯文档响应"（review 发现 N>0 条源码问题，但 git diff 只含 .md 文件）
3. 现有 gate-integrity 的 `.done` 真实性校验不受影响，本次在其基础上叠加实效性维度

## 风险与未知

- **假阳性风险**：某些阶段的 diff 本身就以文档为主（如 1-requirement），需要精准限定检测范围（仅 5/6/7 阶段 + 仅当 review 发现涉及源码问题时触发）
- **技术债登记滥用**：agent 可能把所有发现都标记为"技术债"来绕过代码修复——需要在 prompt 层加约束（技术债登记需显式理由 + 限制比例）
- **与现有 gate_config 的交互**：当前 `gate_config` 值为 both/L2/L3，新增的实效性校验应与现有值兼容（both 时校验，L2-only/L3-only 时也校验——不因审查层级不同而降低代码修复要求）
