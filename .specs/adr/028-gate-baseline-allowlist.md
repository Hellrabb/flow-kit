# ADR-028 · 基线允许清单（ratchet）+ 门禁三态退出码

> 来自 change `health-fix-2026-09b` 阶段 2 DESIGN · D1 / D8
> 编号核对：创建时 `.specs/adr/` 最大编号 = **027**，本 ADR = **028**（未被占用）。
> **教训引用**：ADR-027 的编号更正说明记录了"依据过期的『最大编号』声明 + `ls | head` 截断"导致的重复编号事故 ——
> 本次改用 `ls .specs/adr/ | grep -oE '^[0-9]+' | sort -n | tail -1` 实测最大编号，不依赖任何文档声明。

## Context

`health-fix-2026-09b` 要新增一道隐私门禁（`make check-path-privacy`）并把它接入 `make check`。
落设计时撞到两个反复出现的取舍：

**取舍一：新门禁首跑就有残留，要不要直接红？**

实测：仓库当前**存在**隐私残留，且其中一部分是**本 change 自己新写的**
（`.specs/CONTEXT.md` / `.specs/STATE.md` 的未提交改动即命中）。两类选择：

- **(a) 直接红**：门禁一接入 `make check` 就长期红 —— 而 `ADR-027 ②` 已明确判定
  「**长期红 → 被绕过 → 可信度归零，比没有门禁更糟**」
- **(b) 只暴露不阻塞**：残留可见但永不拦新增泄漏 ⇒ 隐私这条不变量**没有强制力**
  （本 change 的上游 `privacy-path-scrub-2026-09` 的目标正是"前向脱敏"，无强制力即目标落空）

**取舍二：门禁如何表达"这次没查"？**

既有门禁只有 `0/1` 二值。而本判据在**变更集为空**时不适用（无 `.sh` 变更 ⇒ 无对象可查）。
若沿用 `exit 0`，则**"查过了"与"根本没查"不可区分** —— 此点在 L2 与 L3 两条独立审查路径上
被**同时**抓出（L2 F2 / L3 minor2），属高置信度真问题。

既有先例与约束：`ADR-027`（门禁只保证看不见的变可见，不擅改红绿语义）、
`TD-023`（21 处 SC1090 判为 known-acceptable）、以及本 change 自身反复复发的
"判据文本正确但语义不可用"模式（L-119~L-122）。

## Decision

**引入「基线允许清单（ratchet）」工件 + 门禁三态退出码，并把两者的语义固化到本 ADR。**

具体五条：

1. **允许清单是入库工件**，格式为 `file:line` 每行一条 + 理由注释；
   **位置（L3 第 3 轮 critical① 后订正 · 与本 change DESIGN 的 R8 定级裁决对齐）**：**权威副本落常设路径**
   `flow-kit-bundle/flow-kit/reference/<gate>-allowlist.txt`（入库、**不受 change 目录归档影响**），
   change 目录 `.specs/<id>/<gate>-allowlist.txt` 只存**该 change 窗口内的副本**；
   判据读序 = **常设路径 > change 副本 > 两者皆缺 ⇒ fail-closed**（`exit 1` 并**指名缺失路径**，不得静默当空清单）。
   原文「位置随 change 走，**不设全局单文件**（避免不同 change 的基线互相污染）」中，
   **「不设全局单文件」保留**（指不把多个门禁的清单合并成一个文件；权威副本仍按 gate 分文件），
   但「随 change 走」**被本订正取代** —— 实测本仓已有 **91+** 个 change 目录迁入 `.specs/archive/`，
   随 change 走会使**常设门禁**在归档后失去基线（即 R8 所述「最坏情形：静默全量命中或退化为不阻塞」）。
2. **阻塞面只限「非允许清单命中」**：清单内残留 = **只暴露**（依赖它已被人复核并接受）；
   清单外命中 = **阻塞**（`exit 1`）。这是 `ADR-027 ②③` 的直接应用：
   known-acceptable 不升级为 fail，但**新**缺陷必须拦死。
3. **门禁退出码三态**：`0` = 通过 / `1` = 失败 / **`3` = 未验证（SKIP）**。
   **`SKIP ≠ PASS`**：任何消费方（`make check` 聚合、pre-commit hook、AC 断言）
   **必须**显式区分 `3` 与 `0`；把 `3` 当绿灯即为违约。
   **（R1 补充 · make 层映射 · 强制）** 三态**仅适用于「不适用态」判据**，且该判据
   **不得直接挂进 `check:` 先决条件** —— `Makefile:106` 的 `check:` 是 make 先决条件，
   **任何非零即判失败** ⇒ 直接挂入会让干净树/CI 常态下 `make check` **长期红**（撞 `ADR-027 ②`），
   且 pre-commit 阻断纯文档提交（诱发 `--no-verify`）。接入方式固定为：
   **在 `check:` 内以 `if` 包装** —— `3` 转译为「提示 + 不阻塞」，仅 `1` 才 fail。
   **反例（本 change D1 初版即犯）**：把 `rc=3` 同时用在 `check-path-privacy` 上是**串写错误** ——
   该门禁扫 tracked 文件内容，与 `.sh` 变更集无关、**不存在"不适用"态**，故它只有 `0/1`。
4. **失败输出必须指名 `file:line`** —— 依 `ADR-027 ③`「优先扩大**信息**而非**阻塞**」，
   把"无法处置的计数"变成"可处置的信息"。
5. **棘轮方向：只降不升**。允许清单条目数应随修复单调不增；
   任何**新增**清单条目必须在 REVIEW 阶段显式说明"为何这条残留被接受"，
   并在 `.specs/<id>/MINOR-DEFERRED.md` 登记"下次清理窗口"。

**边界（防滥用 · N2 订正）**：本 ADR **不**主张"新门禁可以宽松"，但**确实放宽了 `ADR-027` 的准入判据** ——
初版此处写「不是对它的放宽或替代」，与下方 R12 裁决段的「放宽 / 部分 supersede」**自相矛盾**；
现改为与 R12 一致：**局部放宽 + 部分 supersede，其余条款继续沿用**。
只有当同时满足下面两条时才可适用允许清单：① 该残留**可被机械论证为已声明并接受**
（拿不出论证的一律阻塞）；② 升级为 fail 会导致**长期红或误红**。

> ⚠️ **R12 裁决：本条相对 `ADR-027` 的准入判据**从「**可机械判定无害**」**放宽**为
> 「**已声明并接受**」，且"棘轮只降不升"**无机器判据** —— 属**口径变更，必须显式**。
> **本 ADR 的选择：显式声明为对 `ADR-027` 的「部分 supersede」**（仅准入判据那一条，其余条款继续沿用）。
> 理由：隐私/组织线索类残留**无法机械判定为无害**（是否泄漏取决于仓库可见性与组织政策，属**人工判断**），
> 故 `ADR-027` 的机械判据在此场景**不可用**；强行套用的唯一结果是"全部残留一律阻塞" ⇒ 回到长期红。
> **代价与约束**：放宽后必须补**人工复核环节**（清单入库前逐条复核 + REVIEW 阶段说明），
> 且"只降不升"降级为**流程约束 + REVIEW 检查项**（无机器判据 —— 已知弱点，登记于本 ADR）。
**本 ADR 也不改变既有门禁的红绿语义**；它是 `ADR-027` 在「新增门禁」场景下的具体化。
> **R4/第 3 轮订正**：本行初版结尾为「**不是对它的放宽或替代**」，与上方 `:61-63` 的
> 「局部放宽 + 部分 supersede」**互斥** —— 这是同一矛盾的**第二处**（我在 N2 轮**只改了一处**，
> 属第 5 次「声称已修但工件仍有旧文本」）。现统一为：**除准入判据那一条外**，其余条款继续沿用 `ADR-027`。

## Consequences

### 优点

- ✅ 新门禁**可以立刻接入 `make check` 而不制造长期红** —— 与 `ADR-027 ①`「判据修正 ≠ 阈值升级」一致
- ✅ 隐私这条不变量**获得真实强制力**：新增泄漏必阻塞，既有残留不阻塞
- ✅ `SKIP` 与 `PASS` 可机械区分，消除"没查被当成通过"的假绿通道
- ✅ 允许清单本身成为**可复核工件**（入库 + 理由注释 + 只降不升），比"隐含在代码里的豁免"可审计

### 代价

- ⚠️ **新增一个需人工维护的工件**：清单要复核、要入库、要防腐化（只增不减）
- ⚠️ **`exit 3` 需要全体消费方学习**：`make check` 聚合、pre-commit hook、各 AC 断言
  都必须区分 `3` 与 `0`；漏改一处即留下假绿通道（本 change 已就此在 AC-8 补了断言）
- ⚠️ **清单腐化风险**：若有人不断往清单里加条目，门禁会退化为形式 —— 由第 5 条 + REVIEW 阶段显式说明缓解
- ⚠️ **三态机制的当前使用者 = 0（N2 订正）**：初版称"首个使用者是 `check-path-privacy`"，
  但按 R1 裁决该门禁**只有 0/1**（无 SKIP 态）⇒ **三态部分目前无任何使用者**，
  唯一适用者是本 change 的 **NFR 兼容性判据**（非门禁）。
  ⇒ 抽象风险**高于初版判断**：三态机制尚未被任何 `make check` 门禁验证过；
  若 NFR 判据的包装方案在 TASK 阶段落不了地，应回头收窄本 ADR 的第 3 条。
  允许清单（ratchet）部分则有 1 个使用者（`check-path-privacy`）

### 推翻成本

**中** —— 涉及各门禁实现脚本 + `Makefile` 聚合 + 各 AC 断言 + 可能存在的 CI 配置。
推翻需新增 ADR supersede 本 ADR 与 `ADR-027` 的相关条款。

## Alternatives Considered

### 方案 1 · 直接红（否决）

`make check-path-privacy` 首跑即 `exit 1`。

- ❌ 违反 `ADR-027 ②`：实测残留**含本 change 自己新写的文件** ⇒ 会长期红
- ❌ 长期红 → 被绕过 → 可信度归零（`ADR-027` 已用历史证据判定，`brooks-lint` 的 33/100 时点即前车）

### 方案 2 · 只暴露不阻塞（否决）

门禁只打印结果、恒 `exit 0`。

- ❌ 隐私不变量**无强制力** —— 与 REQUIREMENT 的 US-6 / AC-6 直接冲突
- ❌ 依 `ADR-027` 的边界条款："error 级门禁该拦的要拦死"

### 方案 3 · 全局单文件白名单（否决）

所有门禁共用一个 e.g. `.specs/privacy-allowlist.txt`。

- ❌ 不同 change 的基线互相污染；一个 change 的临时豁免会泄漏到其他 change
- ❌ 无法按 change 归档，`archive/` 时无法冻结

### 方案 4 · 复用 `exit 0/1` 并"约定 SKIP 时打印一句话"（否决）

- ❌ 机器不可判：`make` 聚合与 `[ $? -eq 0 ]` 无法区分"查过了"与"没查"
- ❌ 本 change 的 L2 与 L3 **各自独立**指出该缺陷（L2 F2 / L3 minor2）⇒ 高置信度真问题

## 常设清单自校验规则（T23 · L3 #4 major③ fix · health-fix-2026-09b）

> 来源：`INDEPENDENT-REVIEW-2.md` 末段 L3 #4 major③ fix 原文 ——
> R8 将权威清单落常设路径 `flow-kit-bundle/flow-kit/reference/path-privacy-allowlist.txt`，
> 但「清单被误改 / 被篡改 / 与排除表不同步」时的校验机制缺失（R3 只给「只降不升」原则）。
> 允许清单是门禁的信任根；信任根失真 ⇒ 清单静默失效（fail-open）或排除表误豁免（fail-silent）。
> 以下四条规则由本 ADR 固化为常设允许清单的**自校验契约**，门禁实现见 `check-path-privacy.sh`。

### 规则 ① 格式校验（machine-checked · 强制）

常设允许清单的每一**非注释行**必须匹配 `file:token` 语法：
即 `<路径>:<token>` 形态（对 `check-path-privacy` 即 `file:line` —— 路径在前、冒号分隔、行号在后，
可附 ` # 理由` 尾随注释）。整行注释（`^#`）与空行不计入有效条目，但**任何既非注释、
又不符合 `file:token` 语法的行** ⇒ 门禁 `rc=1` 并在报文里**指名**：
① 清单路径（`path-privacy-allowlist.txt`）；② 违例行号与违例内容（`<行号>: <内容>`）。
理由：格式违例 = 清单**本身**失真（非扫描内容泄漏），必须在读取阶段就拦截，
否则畸形行会被静默吞掉、`ALLOWLIST_COUNT` 会把它计成有效条目 ⇒ 信任根静默失效（fail-open）。

### 规则 ② 内容校验（drift detectable · 强制）

每个有效条目记录**校验和或 git blob 引用**，使清单内容可被**漂移检测**：
任一条目的 `file:line` 指向的文件内容若与入库时记录的 blob 偏离 ⇒ 漂移可见。
理由：允许清单的语义 = 「这条残留已声明并接受」；若被命中行随后被改写，接受前提即不成立，
而纯文本清单无内容锚 ⇒ 漂移不可见。内容锚的实现由 REVIEW 阶段在登记条目时落 git blob sha。

### 规则 ③ 原子更新流程（mktemp + mv · 强制）

清单更新必须走 `mktemp` + `mv` 原子写（写临时文件 → `mv` 覆盖常设路径），
禁止原地改写；且 REVIEW 阶段必须对每条新增条目**显式说明「为何这条残留被接受」**
（为何该命中无法脱敏只能接受）。理由：原子写防中途崩溃留下半写清单（fail-open 半态）；
REVIEW 说明防「为静默命中而偷偷加条目」（ADR-027 ② 的长期红→被绕过→可信度归零同源风险）。

### 规则 ④ 棘轮只降不升（流程约束 · 无机器判据）

允许清单条目数应随修复**单调不增**；条目**只允许减少**，**不允许新增**以静默命中。
任何**新增**清单条目必须在 REVIEW 阶段显式说明接受理由，并在 `.specs/<id>/MINOR-DEFERRED.md`
登记「下次清理窗口」。理由：防清单腐化（不断加条目 ⇒ 门禁退化为形式）。
**已知弱点（显式登记）**：棘轮方向无机器判据，仅流程约束 + REVIEW 检查项（见上文代价段）。

### 排除表与清单路径绑定的双态断言（machine-checked · 强制）

自排除清单 `SELF_EXCLUDE`（`check-path-privacy.sh`）逐条精确路径豁免清单路径本身
（清单文件必然含 PAT 字面：自我引用 / 格式说明 / 审查档讨论）。双态断言固化：
- **(a) 排除生效**：探针注入**清单/排除路径内**（如直接写入 `path-privacy-allowlist.txt`）
  ⇒ **不得**被自身判据误命中（`rc=0`，排除表覆盖了清单路径）。
- **(b) 排除未过度放宽**：探针注入**清单/排除路径外**（如写入 `.specs/CONTEXT.md`）
  ⇒ **必须**命中（`rc=1`），证明排除表没有把面外文件也吞掉。
理由：排除表是 fail-closed 读序之外的**第二道信任根**；若排除失效 ⇒ 清单内探针被自身判据误命中
（自证逻辑自噬）；若排除过度放宽 ⇒ 面外探针被吞（隐私泄漏在排除表下永远绿 ⇒ 假绿）。
两态都必须有机器判据（T23 verify 固化），缺一即信任根失真。
